# ADR-0002: パネルの文字サイズ

| 項目 | 値 |
|------|----|
| Status | **Accepted** |
| Date | 2026-09-27 |
| Binds | instant-translate |
| Decision makers | nlink-jp maintainers |
| Triggered by | PR #1（@anonymousaga）が文字サイズの調整を設定画面のスライダーとして提案した。必要性は採り、形は採らなかった |

## 背景

入力欄と訳文欄の文字はシステムの本文サイズ（macOS 26/27 で 13pt）で描かれ、
変えられない。PR #1 はこれを変える設定画面のスライダー（10〜28pt）を、無関係な
5 つの変更と一緒に提案した。必要性はもっともだが、macOS のアプリが文字サイズを
変えるやり方ではない。

プラットフォームの文書で確認できたこと:

- **⌘+ と ⌘− は標準ショートカット。** HIG の標準表は Shift-Command-=（⌘+）を
  「選択範囲の大きさを上げる」、Command-Hyphen（⌘−）を「下げる」と定め、標準
  ショートカットを別の用途に使わないよう求めている。⌘0 は表に無いが、Safari・
  プレビュー・ブラウザが「実際のサイズ」に使っており、利用者が戻すときに押すキー。
- **拡大するのは内容で、操作部品ではない。** Apple の Larger Text 評価基準:
  「繰り返し出てくる決まったナビゲーション要素より先に、主な内容の領域を拡大する」、
  本文は標準の「少なくとも 200%」まで拡大できること。
- **システムの文字サイズ設定は、macOS ではサードパーティ製アプリにほぼ届かない。**
  明言しているのは二次情報のみ（Finder・メール・サイドバーは従う）。Apple の基準は
  アプリ内の操作を認めたうえで、システム設定が効く場合はそれに従うことを勧める。
  この Mac では未確認 — 確かめるにはシステム設定を変える必要があるので、
  メンテナに委ねる。
- **ショートカットは他のキーボード配列向けに自動で読み替えられる**
  （`KeyboardShortcut.Localization`、`NSMenuItem.allowsAutomaticKeyEquivalentLocalization`、
  既定で有効）。ただし読み替えるのは、そのキーが今の配列で**押せない**ときだけ。
  日本語配列では `+` は押せる（Shift-;）ので読み替えは起きない見込み。そこで ⌘+ が
  実際にどう届くか、英語配列で Shift なしの ⌘= が効くかは文書に無く、実測が要る。

このアプリにはメニューバーが無い（`LSUIElement`）ので、ショートカットがあることを
アプリの中で示す場所が無い。

## 決定

### 決定 1: パネルで ⌘+ / ⌘− / ⌘0、設定画面に操作部品は置かない

パネルが key のあいだ、⌘+ で拡大、⌘− で縮小、⌘0 で元に戻す。設定画面には
**スライダーを置かない**。3 つのショートカットを示す説明を 1 行だけ置き（アプリ内で
知る唯一の場所）、README にも書く。

ショートカットは `PanelView` で、見えないボタンに `.keyboardShortcut` で付ける。パネルが
既に ⌘↩（翻訳）に使っている仕組み。ショートカットは修飾キーまで**完全一致**で照合される
ので、拡大は 3 通りに結び付ける:

| 結び付け | 何を押すとこうなるか |
|----------|----------------------|
| `"+"` + ⌘⇧ | メイン列の `+`。英語配列（`=` キー）でも日本語配列（`;` キー）でも Shift 付き。Shift + テンキーの `+` も |
| `"+"` + ⌘ | テンキーの `+`。Shift なしで届く |
| `"="` + ⌘ | 英語配列の ⌘=。ブラウザも受け付ける Shift なしの別名 |

⌘−（メイン列・テンキー）と ⌘0 は 1 つずつでよい。

### 決定 2: 大きさが変わるもの

内容だけ: **入力欄の文字**、その**空欄時の案内文**、**訳文**。見出し、ピッカーと
その「(…)」ヒント、状態表示の行、失敗メッセージ、ボタンは大きさを変えない。
Apple の「操作部品より内容」の指針に沿い、バランスの懸念にもそのまま答える —
文字が大きくなってもレイアウトが崩れないのは、操作部品が動かないから。

### 決定 3: システムの本文サイズを基準にした固定の段階

大きさは、大きくなるほど間隔が広がる段階を移動する:

```
10 · 11 · 12 · 13 · 14 · 16 · 18 · 20 · 24 · 28   (pt)
```

28pt は本文 13pt の 215% で、Apple の 200% を超える。1pt 刻みは、13 から 28 まで
15 回押すことになるので採らない。

保存する値は、利用者が ⌘+ か ⌘− を押すまでは **「指定なし」** で、⌘0 でそこに戻る。
指定なしのときは欄がシステムの本文サイズを使うので、いつかシステムの文字サイズ設定が
このアプリに届くようになれば、既定値はそれに従う。どの大きさからでも ⌘+ / ⌘− は
段階のうち「厳密に大きい / 小さい」次の値へ移るので、段階に無い本文サイズからでも
素直に動く。両端ではキーは何もしない。

移動の規則は**純関数**（現在の大きさ・方向 → 次の大きさ）にし、`LanguagePolicy` や
`AutoTranslatePolicy` と同じく単体テストする。

### 決定 4: 選んだ大きさを覚える

選んだ大きさは UserDefaults に保存し（無ければ指定なし）、起動時に戻す。読みやすさの
必要は起動ごとに変わらず、⌘0 はいつでも 1 回で済む。入力言語のピンや訳先の指定は
文ごとの指定なので意図的に揮発させているが、これは人ごとの好み。

## 結果

- macOS の慣習どおりに文字サイズを変えられる。設定画面に操作部品は増えず、
  説明が 1 行増えるだけ。
- 操作部品は大きくならないので、大きな文字でもパネルが横にあふれない。
- 28pt でも入力欄と訳文欄の最小の高さは 80pt のまま — それぞれ約 2 行。これで
  よいか、最小の高さも大きくするかは、前もってではなく見て決める — 下の結果 2 を参照。
- キーを押さない利用者の既定値は変わらない（システムの本文サイズ）。PR #1 の
  スライダーは全員を 13pt から 14pt に変えるところだった。
- UserDefaults のキーが 1 つ増える。`SettingsKey.registerDefaults()` には登録しない
  （無いことが意味を持つ）。

## 未決事項の結果（試作、2026-09-27）

メンテナが手で実測した。キーボードは JIS 並び、入力メソッドはかわせみで、日本語モードと
英字モードの両方。受け取った ⌘ 付きキーイベント（`keyCode`・文字・修飾キー・パネルが
処理したか）を記録する一時的なビルドを使った。先に試した自動テストは破棄した: US 配列の
仮想キーコードを送っていたが、この配列ではそれが別のキーで（キーコード 24 は JIS では `=`
ではなく `^`）、`+` も `=` も一度も送れていなかった。

1. **キーの届き方。**

   | 押したキー | 届いた形 | 処理されたか |
   |------------|----------|--------------|
   | ⌘ + メイン列の `+`（Shift-`;`、キーコード 41） | `"+"`、⌘⇧ | された |
   | ⌘ + テンキーの `+`（キーコード 69） | `"+"`、⌘ | `"+"` + ⌘ の結び付けを足してから、された |
   | ⌘ + Shift + テンキーの `+` | `"+"`、⌘⇧ | された |
   | ⌘ + メイン列の `-`（キーコード 27）／テンキーの `-`（78） | `"-"`、⌘ | された |
   | ⌘ + テンキーの `0`（キーコード 82） | `"0"`、⌘ | された |

   日本語モードと英字モードで同じ。処理されなかった ⌘ 付きキーはテキストビューまで届いて
   警告音を鳴らす — テンキー用の結び付けが無いことは、これで分かった。
   **未計測:** 英語配列（⌘⇧= と ⌘=）と、アプリが**非アクティブ**なとき — どの試行でも、
   ホットキーでパネルを開くとアプリはアクティブになっていた。
2. **最小サイズ。** パネルを最小まで縮めるとレイアウトが崩れた — ただし標準の 13pt でも
   同じだった。幅が固定の言語ピッカーが行を埋め、「(…)」ヒントが 1 文字ずつ折り返され、
   Translate ボタンが細い帯になり、Copy / Quit の行が押し出される。ピッカーの行は文字サイズを
   見ていないので、これはパネルの最小サイズ（320 × 320pt）の既存の不具合で、別に直す。
   欄の最小の高さ 80pt は、その修正のあとで 28pt で見直す。
3. **IME の変換中。** かな漢字変換の途中で ⌘+ を押しても、未確定文字列はそのまま。新しい
   大きさは変換を確定してから適用される（大きさの変更は `hasMarkedText()` が外れるまで待つ。
   `SourceTextView.updateNSView` の文字列の書き換えと同じ扱い）。
4. **キャレット。** 大きさを変えてもキャレットは動かなかった。長い訳文のときの訳文欄の
   スクロール位置は、個別には確かめていない。

## 検討した代替案

**A1. 設定画面のスライダー（PR #1 の形）。** 不採用: macOS のアプリが文字サイズを
変えるやり方ではなく、全員の既定値を変える（13 → 14pt）。メンテナの判断。

**A2. システムの文字サイズ設定に従うだけ。** 唯一の手段としては不採用: macOS では
届くアプリが少なく、押すものが何も無くなる。既定値としては採用 —「指定なし」は
システムの本文サイズを意味する。

**A3. パネル全体（操作部品も）を拡大する。** Apple 自身の指針により不採用。
ピッカーやボタンが大きくなると、1 行の操作列が真っ先に詰まる。

**A4. 1pt 刻み。** 不採用: 既定から 200% まで 15 回押すことになる。

**A5. メニューコマンド（表示メニューの `CommandGroup`）。** このアプリには見える
メニューバーが無いので、メニューは利用者に何も見せない。また、non-activating パネルが
key でアプリが非アクティブなときに、メインメニュー経由のキー配送が届くかは未確認。
`.keyboardShortcut` はこのパネルで既に使っている（⌘↩）。

**A6. ローカルの `keyDown` モニタで文字を照合する。** ビューの状態によらず効くが、
システムの配列読み替えを迂回し、配列ごとの文字照合を自前で持つことになる。
不要だった: 結果 1 のとおり、届く形ごとに結び付ければ `.keyboardShortcut` は日本語配列で
発火する。
